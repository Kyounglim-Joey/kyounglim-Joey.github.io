# Analytics 설계 문서

## 1. 도구 비교와 선택

비교 기준은 2026년 11월 확인 기준입니다. 요금과 한도는 바뀔 수 있으니 가입 시 공식 페이지에서 다시 확인하세요.

| 기준 | GA4 | Cloudflare Web Analytics | Plausible | **Umami Cloud (선택)** |
|---|---|---|---|---|
| 비용 | 무료 | 무료 | 유료 (월 $9~, 무료 플랜 없음, 체험만 제공) | **무료 Hobby** (월 10만 이벤트, 보관 6개월) |
| GitHub Pages 호환 | O (스크립트) | O (JS beacon, 비프록시 사이트 10개 한도) | O | O |
| 설치·관리 | 중~상 (속성·맞춤 측정기준 설정, 동의 관리 필요) | 하 | 하 | 하 |
| PV / 순방문자 | O (쿠키 기반) | O (추정) | O (쿠키 없는 추정) | O (쿠키 없는 추정) |
| 참여 시간 | **O (기본 제공, 가장 정교)** | 부분적 | **O (활성 시간 기반 time on page, scroll depth 기본 제공)** | △ 방문 시간만 기본 제공 → **이 사이트에서 자체 구현** |
| 커스텀 이벤트 | O | **X (미지원)** | O (goals + props) | **O (속성 포함)** |
| Referrer / 지역 / 기기 | O | O | O | O |
| 경로·퍼널 | O (Explorations) | X | 퍼널은 상위 플랜 | **O (Journey, Funnel, Goals)** |
| 개인정보 보호 | 쿠키 사용, Google로 전송 → EU 방문자는 사전 동의 필요 | 우수 (쿠키 없음) | 우수 (쿠키 없음) | 우수 (쿠키 없음, 오픈소스) |
| 대시보드 편의성 | 복잡 | 단순 | 매우 쉬움 | 쉬움 |
| 확장성 | 매우 높음 (BigQuery 등) | 낮음 | 중간 | 중간 (API, 필요하면 셀프호스팅) |

### 선택 이유: Umami Cloud

이 사이트의 목적은 방문자 수보다 "교수진과 입학사정관이 어떤 콘텐츠를 실제로 읽는가"를 아는 것입니다. 그러려면 다음 세 가지가 필요합니다.

1. 속성이 붙는 커스텀 이벤트 (어떤 프로젝트인지, 어디서 클릭했는지)
2. 경로 분석 (Journey, Funnel)
3. 참여 시간 측정

이 세 가지를 **무료로, 쿠키 없이** 모두 만족하는 것은 Umami입니다.

- **Cloudflare**는 커스텀 이벤트를 지원하지 않아 제외했습니다.
- **Plausible**은 참여 시간과 스크롤 깊이를 기본 제공하는 장점이 있지만 유료입니다. 월 $9를 낼 의향이 있다면 가장 깔끔한 대안이고, `analytics.js`의 이벤트 이름 체계를 거의 그대로 옮길 수 있습니다.
- **GA4**는 기능상 가장 강력하지만, 쿠키와 Google 전송 때문에 동의 배너가 필요해집니다. 보안 포트폴리오에서 "필요 이상으로 추적한다"는 인상을 줄 위험도 있습니다.

Umami의 약점인 페이지별 참여 시간과 스크롤 깊이는 `public/js/analytics.js`에서 직접 측정해 `page_engagement` 이벤트로 보내도록 보완했습니다. 추적 스크립트는 Umami 하나만 설치했습니다.

## 2. 무엇을 어떻게 수집하나

### 2-1. 자동 수집 (Umami)

페이지뷰, 방문자·방문 수, 이탈률, 방문 시간, Referrer 도메인, 국가·지역·도시, 기기, 브라우저, OS, 언어가 자동으로 수집됩니다.

- **순방문자(Unique Visitors)는 추정치입니다.** Umami는 쿠키 대신 요청 정보(IP·User-Agent 등)와 주기적으로 바뀌는 salt로 익명 식별자를 만듭니다. 같은 사람도 기기·브라우저·네트워크가 바뀌거나 salt가 교체되면 새 방문자로 집계됩니다. 반대로 같은 네트워크·브라우저를 쓰는 서로 다른 사람이 하나로 합쳐질 수도 있습니다.
- **재방문자 비율**은 Retention 리포트로 대략 확인할 수 있지만, 쿠키가 없으므로 정확하지 않습니다.
- **봇:** Umami 서버가 User-Agent 기반으로 알려진 봇을 걸러냅니다. 다만 브라우저를 흉내 내는 봇까지 완벽하게 거르지는 못합니다.

### 2-2. 커스텀 이벤트 (`public/js/analytics.js`)

| 이벤트 | 발생 조건 | 속성 |
|---|---|---|
| `cv_download` | CV PDF 링크 클릭 | location (hero / cv-page / footer …), file |
| `github_profile_click` | GitHub 프로필 링크 클릭 | location |
| `linkedin_click` | LinkedIn 링크 클릭 (URL 입력 후 활성화) | location |
| `email_click` | mailto 링크 클릭 | location |
| `contact_click` | CV & Contact 페이지로 가는 링크 클릭 | location |
| `project_view` | 프로젝트 상세 페이지 로드 (1회) | project |
| `project_github_click` | 프로젝트 저장소 링크 클릭 | project, location |
| `research_interest_view` | Research Interests 영역이 50% 이상, 1초 이상 화면에 보임 (페이지당 1회) | section |
| `outbound_click` | 그 밖의 외부 링크 클릭 | domain |
| `page_engagement` | 탭이 숨겨지거나 페이지를 떠날 때 1회 | engaged_s, engaged_bucket, scroll_pct |

모든 이벤트에는 공통 속성 `page`(경로), `device`(mobile / tablet / desktop), `ref_cat`(direct / search / github / linkedin / academic / email / social / internal / other)이 붙습니다. 상세 페이지 이벤트에는 `project`도 붙습니다. 이벤트 시각은 Umami 서버가 기록합니다.

**중복 방지 규칙**
- 조회 이벤트(project_view, research_interest_view, page_engagement)는 페이지 로드당 1회만 기록합니다.
- 클릭 이벤트는 같은 대상을 2초 안에 다시 클릭하면 무시합니다. 더블클릭이 2건으로 잡히지 않게 하기 위함입니다.
- 메일 링크를 한 번 클릭하면 `email_click`만 기록되고 `contact_click`은 함께 기록되지 않습니다.

### 2-3. 참여 시간 측정 방식과 한계

- 1초 단위로 다음 세 조건을 모두 만족할 때만 시간을 셉니다.
  - 탭이 화면에 보이고 (`visibilityState`)
  - 창에 포커스가 있고 (`hasFocus`)
  - 최근 45초 안에 스크롤·키보드·포인터·터치 입력이 있었음
- 백그라운드 탭에 머문 시간, 자리를 비운 시간, 다른 창을 보던 시간은 제외됩니다.
- 탭이 처음 숨겨지거나 페이지를 떠날 때 **한 번만** 전송합니다. 따라서 탭을 잠깐 전환했다가 돌아와 더 읽은 시간은 집계되지 않아 **과소 추정**될 수 있습니다.
- 브라우저가 강제 종료되는 경우, 일부 모바일 브라우저, 광고 차단기 사용 시에는 전송되지 않을 수 있습니다.
- 45초 동안 입력 없이 긴 문단을 읽는 경우도 일부 과소 추정됩니다.
- **결론적으로 정확한 체류 시간이 아니라 "적극적으로 보고 있던 시간"의 보수적 추정치**입니다. 상대 비교(프로젝트 A vs B)에 쓰고, 절대값으로 해석하지 마세요.
- `scroll_pct`는 0 / 25 / 50 / 75 / 100 구간이며, 짧아서 스크롤이 없는 페이지는 100으로 기록됩니다.

## 3. 개인정보 보호·보안 설계

| 원칙 | 구현 |
|---|---|
| 최소 수집 | 이벤트 속성을 허용 목록(allow-list)으로 제한하고 문자열을 120자로 잘라 보냅니다 (`umami-guard.js`) |
| 익명·집계 | 쿠키 없음, 로그인·폼 없음, 신원 식별 시도 없음 |
| Fingerprinting 지양 | 캔버스·폰트 등 지문 수집을 하지 않습니다. 기기 구분은 화면 폭 기반 3구간뿐입니다 |
| 제3자 쿠키 | 없음 |
| IP 직접 저장 | 사이트는 IP를 다루지 않습니다. Umami가 요청 처리 중 위치를 추정하는 데 사용합니다 |
| 민감 URL 파라미터 | URL의 `?`와 `#` 뒤를 제거하고, Referrer는 origin만 남깁니다 (예: `https://www.google.com/`) |
| 관리자 접근 통제 | 통계는 Umami 로그인 화면에서만 볼 수 있습니다. 사이트에 대시보드나 비밀값이 없습니다. Share URL은 끈 상태로 유지하세요 |
| 비밀값 비노출 | Website ID만 빌드 시 주입합니다 (공개 식별자). API 키는 사용하지 않습니다 |
| DNT / GPC | `data-do-not-track="true"`로 DNT를 따르고, GPC 신호가 있으면 전송을 취소합니다 |
| 거부권 | /privacy/ 페이지의 opt-out 토글 (`localStorage umami.disabled`) |
| 브라우저 보안 | CSP meta (script-src는 self와 cloud.umami.is만 허용), referrer policy `strict-origin-when-cross-origin` |
| 기기 저장소 | Analytics 목적으로는 아무것도 저장하지 않습니다. 테마 선택과 opt-out 플래그만 저장하며, 둘 다 사용자가 직접 선택한 설정입니다 |

### Cookie Consent가 필요한가?

- Umami는 쿠키를 쓰지 않고, 이 사이트도 Analytics 목적으로 기기에 아무것도 저장하지 않습니다. 개인 식별 데이터도 저장하지 않습니다. 이런 구성에서는 일반적으로 **동의 배너 없이 고지만으로 운영하는 것이 업계 관행**이고, Umami도 GDPR 대응을 그렇게 설명합니다.
- 다만 IP를 처리 과정에서 일시적으로 사용하므로, 엄격한 해석에서는 "정당한 이익"을 근거로 한 처리에 해당합니다. 그래서 /privacy/ 페이지에 처리 목적, 수집하지 않는 항목, 거부 방법을 공개했습니다.
- 한국 개인정보보호법 관점에서도 개인을 식별할 수 있는 정보를 수집하지 않는 구성입니다.
- **GA4로 바꾸거나 Session Replay 등을 추가하면 EU 방문자를 위한 동의 배너가 필요해집니다.**
- 저는 법률 전문가가 아닙니다. 위 내용은 기술 구성에 대한 설명이지 법률 자문이 아닙니다.

## 4. 5가지 핵심 질문을 확인하는 방법

| 질문 | 확인 방법 |
|---|---|
| 1. Home에서 About / Projects / Experience 중 어디로 가는가? | Reports → **Journey**: 시작 단계를 `/`로 두고 다음 단계 분포를 봅니다. 보조로 Pages에서 `/` 필터 후 다음 페이지를 확인합니다 |
| 2. 세 ML 프로젝트 중 무엇을 가장 많이 보는가? | Events → `project_view` → 속성 `project`별 건수. 또는 Pages에서 `/projects/…` 3개를 비교합니다 |
| 3. ET5 상세 페이지 방문자는 얼마나 머무는가? | Events → `page_engagement`에 필터 `project = et5_summarization` → `engaged_bucket` 분포(0-10s, 10-30s, 30-60s, 1-3m, 3-10m, 10m+)와 `scroll_pct` 분포 |
| 4. CV 다운로드 전에 어떤 페이지를 보는가? | Reports → **Journey**: 종료 단계를 이벤트 `cv_download`로 둡니다. 또는 **Funnel**(예: `/` → `/projects/*` → `cv_download`). `cv_download`의 `page`·`location` 속성으로 어느 화면 어느 버튼에서 받았는지도 확인할 수 있습니다 |
| 5. 어느 페이지에서 방문이 끝나는가? | Pages 패널 **Exit** 탭, 또는 Journey의 종료 지점 |

**해석 시 주의할 점**

- `ref_cat = academic`(.edu, .ac.kr 등)은 "학교 도메인 웹페이지에서 링크를 타고 왔다"는 뜻일 뿐입니다. **어느 학교의 입학사정관이나 교수가 방문했다고 판단할 수는 없습니다.** 지원 포털이나 이메일에서 클릭하면 Referrer가 비어 `direct`로 잡히는 경우가 많습니다.
- 국가와 도시는 IP 기반 추정이라 VPN이나 기관 네트워크에서는 틀릴 수 있습니다.
- 방문 수가 적을 때(예: 월 수십 건)는 비율보다 개별 흐름을 질적으로 보는 편이 의미 있습니다.
- 지원서를 제출한 날 전후로 변화를 비교하면 좋습니다.

`tests/analytics.test.py` 실행 결과 **24/24 통과**:

- CV 더블클릭 시 1건만 기록, location 속성 포함
- GitHub 프로필, 이메일, contact 클릭 이벤트
- 프로젝트 3개 각각 `project_view` 1회 기록, 페이지뷰도 경로별로 구분됨
- 저장소 클릭에 프로젝트명 포함
- 참여 시간: 6초 활동 후 포커스 해제 4초 → `engaged_s=6` (비활성 시간 제외 확인), 스크롤 구간 기록
- opt-out, GPC, DNT 각각 전송 0건
- 전체 탐색 중 모든 payload에 쿼리 문자열·이메일·비밀값 없음, 허용 목록 외 속성 없음

**검증하지 못한 것:** 실제 Umami Cloud 수집과 대시보드 표시는 계정 연결 후에만 확인할 수 있습니다(SETUP_GUIDE 4-4). 테스트용 스텁은 Umami의 동작을 흉내 낸 것으로, Umami의 실제 전송 형식과 다를 수 있습니다.

**성능:** 사이트 자체 JS는 약 15 KB(압축 전)이고, 모두 `defer`로 로드합니다. Umami 스크립트도 수 KB 수준의 `defer` 로드입니다. 외부 폰트와 프레임워크 런타임은 없습니다.
